# ML methodology

This document describes what the ML work does, how it was built and what it does not show. Results are in `EVALUATION.md`.

## Scope and honesty

- All models are trained and evaluated on **synthetic telemetry** generated by the repository's simulator (`backend/simulator_v2`). Fault injection and labels come from the simulator. No public or real-world dataset is used.
- The synthetic evaluation does **not** show real-world accuracy, calibrated probabilities or production reliability.
- Three things are kept separate:
  1. **Offline evaluation:** model training and scoring on exported datasets (`backend/ml/`).
  2. **Experimental live inference:** the outage adapter scores telemetry stored for a host, on request (`backend/app/ml_inference/`).
  3. **Public product functionality:** what the deployed dashboard and API expose. As of this writing, no ML output is part of it.

## Data

- **Generator:** `python -m simulator_v2 generate --seed S --workers W --out <dir>`. Seed 0 is the only seed generated and evaluated so far; seeds 1 to 4 are not generated.
- **Observations:** each run has per-metric observations (CPU, memory, disk per mount, network counters per interface), with an observation time and an envelope time. The feature pipeline uses the envelope time for availability, so only data the system had at decision time is used.
- **Faults:** each run records fault events with impact windows. Decision points inside a fault impact window are the positive class for anomaly detection.
- **Splits:** `train`, `val`, `test_iid` and `test_ood`. Only `train` and `val` have been used. The test splits have not been opened, and no holdout result exists.

## Feature engineering

- `ml/features.py` (feature version 1.1) builds rolling features per decision point from six series: CPU, memory, two disks (root and data), and receive/transmit counters. Windows are 300, 900 and 3600 seconds.
- Each feature has an explicit availability rule. Missing or stale input is NaN, not zero, and sufficiency rules mirror `ml/availability.py` (at least one hour of history, minimum interval count, freshness at 3 x the series cadence).
- Four network rate-spread features are defined but not produced: they were NaN in every training row, so the feature module does not compute them. The saved outage model still lists them as inputs; they are supplied as NaN, matching training.
- **Disk roles.** The two disk inputs are the root and data mounts. The simulator labels them `/` and `/data`. Live hosts map their mounts explicitly per host. Nothing assumes that `C:` is root, and the worst mount is never substituted for either input (see `ml_inference/inputs.py`).

## Anomaly detection (separate task)

- **Label:** a decision point is anomalous if it lies in a fault impact window.
- **Learned detector:** ECOD (pyod), fitted only on benign training rows, with a threshold at the 0.99 quantile of benign training calibration scores. Isolation Forest and COPOD were evaluated in the offline study; only ECOD was exported as an artifact.
- **Rule-based baselines:** a fixed 85% threshold on CPU or memory, and a 5-minute z-score against benign training statistics. These are not ML and are reported as rules.
- **Silence classes** are defined from observation timestamps, not from the simulator's family label. A 60-second tail rule is used.

## Outage prediction (30-minute horizon)

- **Model:** XGBoost, with logistic regression and a rule baseline also evaluated offline. The saved XGBoost model, its schema and its validation-chosen threshold are used unchanged by the adapter.
- **Negative thinning:** training keeps every positive decision and every tenth negative decision, with a corresponding `scale_pos_weight`. The analytic correction ln(w x stride) restores the base rate in the logits; isotonic calibration, where evaluated, was fitted on training runs only.
- **Output label:** the adapter returns a `risk_score`, not a probability, labelled experimental. The saved model is marked preliminary, and its validation skill against the base rate is negative.
- **Training data for the saved model:** the schema records 39,329 rows, 300 positive rows, 10 positive windows and 2 runs. The model is therefore trained on very little incident data.

## Live inference adapter

1. Read the host's stored envelopes for the last six hours.
2. Build per-series samples, keeping labels (mount, interface) and both timestamps.
3. Resolve the disk roles from the explicit mapping. Fail closed if the mapping is missing, incomplete, ambiguous, or names a mount that is not present.
4. Require one network interface, at least one hour of history, and fresh inputs.
5. Build the feature row with the verified pipeline and score it with the saved model.

Verified: features rebuilt from raw simulator observations for run `r0000` match the saved training features on all 192 columns for 50 decision points, with no NaN mismatches (largest difference about 1e-7 relative, float32 precision). Scores through the adapter match saved-row scores for six sampled decision points (maximum difference 4.5e-6).

## Limitations

- Synthetic data only. Real telemetry has different cadence, metric coverage and fault behaviour.
- Very small positive set for the outage model (10 windows).
- Weak validation performance for both tasks (see `EVALUATION.md`).
- Live disk mapping is an operator input, not yet stored per host.
- Scores are computed on request and not yet persisted, so there is no history.
